## 4. 性能记录（不设数值门槛）

按 `docs/Decisions.md` 第 14.10 节：本节数据是观察材料，不是自动判定门槛。
占用是否可接受由项目所有者判断，结论以「通过／不通过」写入验收记录与
Release 说明，不换算成固定预算数字。

KDE 连续运行三小时；Windows 记录启动时间与一次常规使用后的占用即可。期间正常
触发移动、气泡、投喂、设置、隐藏和一次生命周期恢复，不只静置。

> **KDE 的三小时连续运行已完成，但采样密度低于本节原本的要求。**
>
> - **密集采样段**：进程 17:42:03 启动，18:25:35–18:33:05 以 30 s 间隔连采 16 个
>   样本（约 7.5 分钟），期间穿插投喂与设置窗口开关。用 `/proc/PID/stat` 的
>   `utime+stime` 差值求瞬时 CPU%，未使用 `ps` 的 `%cpu`。
> - **三小时段**：连续运行三小时，只在开始与结束各取一次读数——
>   CPU 单核 `1.32%` → `1.53%`，内存 `87.3 MB` → `87.3 MB`。没有中段读数，
>   也没有连续均值。
>
> 因此第 11.3 节「连续运行至少三小时」已满足；未满足的是本节要求的三点读数与
> 连续均值。三小时段内存零增长是这批数据里最有意义的一条。
>
> **两个平台的 CPU 列单位不同，不能直接相比。** Linux 侧脚本按
> `dticks/HZ/dt*100` 计算，是**单核百分比**；Windows 侧脚本额外除以逻辑核数
> （24），是**整机容量百分比**。下表 Windows 行同时给出两种口径。

**采样方式**（`1.1.0` 人工检查点 A 的教训，见 `docs/Plans/DevelopmentStatus-1.1.md`）：

- CPU **不要用 `ps` 的 `%cpu`**——它是进程存活期的累计平均，对定时器驱动的动画
  进程系统性偏低，检查点 A 的 5 分钟采样因此得到几乎全为 `0.00` 的一列废数据。
  Linux 用 `pidstat -p <PID> <间隔>`，或对 `/proc/<PID>/stat` 的 `utime`＋`stime`
  求两次差值。
- 磁盘读写若取 `read_bytes`／`write_bytes`，只统计落到块设备的 I/O，配置写入停在
  页缓存里看不到，不能据此判断有没有落盘。
- 记录连续均值，不只记三个时间点的瞬时值。
