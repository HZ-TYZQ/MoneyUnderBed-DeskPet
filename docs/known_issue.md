# 已知问题

最后更新：2026-10-02

本文记录已经确认、但评估后影响不大而暂不修复的问题。每条都写明触发条件，
便于判断是否碰上了它；修复时从本文删除对应条目。

## 1. `--scale` 覆盖会在下一次保存时写回配置文件

- **现象**：用 `--scale` 启动后，只要发生任何一次设置保存（例如在托盘或右键菜单里
  切换活动模式），命令行指定的倍率就会写进配置文件，下次不带参数启动也沿用它。
- **触发条件**：使用 `--scale`。该参数只用于开发和排查，普通用户不会用到。
- **原因**：`SettingsController::applyForThisRunOnly()` 把覆盖值并入了唯一的运行时
  设置，之后 `persistNow()` 整份写盘（`src/app/SettingsController.cpp`）。
- **修复方向**：控制器单独记住本次运行的覆盖值，落盘时用已保存的倍率替换它，
  除非用户在本次运行中亲自改过倍率。

## 2. 把显示倍率改小后，角色会短暂浮在半空

- **现象**：例如从 `3×` 改到 `1×`，角色底边离屏幕底部约 222 像素，随后斜着走回
  底部或在下一次待机时返回。
- **触发条件**：在设置里把显示倍率调小。
- **原因**：窗口缩放时左上角不动，底边随之上移（`CharacterPresenter::applySettings()`）。
- **修复方向**：缩放前后保持窗口底边不变，再夹回可用区域。

## 3. 行走速度设为 8–9 像素/秒时，角色向右跑却一直朝左

- **现象**：速度低于转身阈值时，跑动方向与朝向相反。
- **触发条件**：在高级设置里把「行走速度」调到最低的 8 或 9 像素/秒；三个预设档位
  都不会触发。
- **原因**：转身需要越过死区加滞后量 `6 + 4 = 10` 像素/秒
  （`src/character/Direction.cpp`），而设置允许的最低速度是 8
  （`src/core/Settings.h` 的 `kSpeedPxPerSec`）。
- **修复方向**：把速度下限提到 10 以上，或让转身阈值随速度缩放。

## 4. 气泡贴到屏幕右边或下边时多留 1 像素

- **现象**：气泡贴边时左、上、右、下四边分别留 8、8、9、9 像素。
- **触发条件**：角色靠近屏幕右边或下边。
- **原因**：`BubbleRenderer::placeFor()` 计算右、下边界时用了 `QRect::right()` 与
  `bottom()`，少加了 1。
- **修复方向**：上界改为 `right() + 1 - margin - width`，下边同理。

## 5. Linux 上几乎同时启动两次，可能出现两个实例

- **现象**：两个进程都成为主实例，此后再次启动只会唤回其中一个。
- **触发条件**：第二个进程连接失败之后、清理旧端点之前，第一个进程恰好开始监听。
  需要两次启动相隔毫秒级，现实中极少发生。
- **原因**：Linux 没有独立的实例锁，`SingleInstance::acquire()` 的
  `QLocalServer::removeServer()` 会删掉刚建立的端点（`src/app/SingleInstance.cpp`）。
- **修复方向**：Linux 也使用独立锁（例如 `QLockFile`），只有取得锁之后才清理端点。

## 6. 同一版本标签重跑打包时，对应源码 Release 只核对文件个数

- **现象**：两次运行之间如果 runner 镜像更新，AppImage 会捆绑不同版本的 Ubuntu
  系统库，二进制被覆盖上传进草稿 Release；但已存在的对应源码 Release 只比较文件
  数量，数量一致就照样通过，二者可能对不上。
- **触发条件**：对同一个版本标签重新运行工作流，且期间 runner 镜像恰好更新。
- **位置**：`.github/workflows/ci.yml` 的 `release` 作业，「Publish corresponding-source
  release」一步。
- **修复方向**：改为比对 `SHA256SUMS` 与文件名清单，不一致时报错。

## 7. 上游覆盖 AppImage 运行时的 `continuous` 发布后，Linux 打包会失败

- **现象**：Linux 作业在「Download pinned AppImage tooling」一组里报
  `runtime-x86_64: FAILED`，构建停止。
- **触发条件**：上游 `AppImage/type2-runtime` 用新提交重新发布 `continuous`。2026-09-28
  已发生过一次，当时把锁定从 `75849dce` 改到了 `8f39b89`。
- **原因**：运行时只有 `continuous` 这一个持续更新的下载地址，`packaging/pins.env`
  锁定的是其中某一次构建的 SHA-256。校验失败是有意的安全失败：运行时静态链接了
  libfuse 等组件，不能在对应源码不变的情况下悄悄换掉二进制。
- **处理方法**：核对上游新提交是否改动了依赖版本（`scripts/` 下的构建脚本），
  然后同时更新 `packaging/pins.env` 的 `APPIMAGE_RUNTIME_SHA256`、
  `APPIMAGE_RUNTIME_COMMIT` 与 `packaging/licenses/appimage-runtime.txt` 里的提交和哈希；
  依赖版本若有变化，还要同步更新对应源码与许可文本。
- **彻底修复方向**：改为自行托管一份固定的运行时，或锁定上游不会移动的发布。
