### Windows 实测（2026-08-27）

项目所有者用 run 33001629207 的探针包（commit `017fd14e`，SHA-256 已核对）在 150% 缩放的单显示器上运行了 10 个用例。完整结果见 `docs/WindowsFeasibilityResults.md`。

通过的核心能力：帧间隔（596 采样，平均 100.00 ms）、自主移动（132/132 请求与实际位置一致）、透明背景、像素锐利、置顶、不进任务栏、启动不抢焦点、原生穿透。

复测后补齐了 `hittest`、`drag-system`、`drag-manual`、`lifecycle` 与 `passthrough-qt`，14 个用例全部核心能力通过，**没有任何失败项**：

- `hittest`：149 次角色点击**全部** `sprite_alpha=255`，另有 18 次从透明区穿到下层。掩码 98 个矩形，包围盒 `38,44,72,178` 明显小于 `138x222` 窗口。`docs/Decisions.md` 第 3.4 节在 Windows 上成立。
- `drag-manual`：11 702 次移动，请求与实际位置 **0 / 11 730** 不一致。
- `drag-system`：5 次请求全部 `accepted=true`。
- `lifecycle`：`window_close` → `exit`，干净退出。

**窗口重建问题没有复现。** 两条穿透路径与 `topmost` 的所有切换都是 `rebuilt=false`。计划 6.1 设想的「复现窗口重建后才引入 Win32」这个触发条件不成立。

**首轮对 `passthrough-qt` 的判断是错的。** 首轮只记到 1 次角色点击、0 次穿透，与 `passthrough-native` 的 43/49 形成 92 比 1，据此曾初步判断 Qt 路径无效。复测数据是 135/122 与 189/181，并且逐段核对开关与点击的对应关系，两条路径全程正确。首轮异常来自测试环境（下层点击靶很可能被 PowerShell 遮住，且那轮落在角色上的点击远少于复测轮）。教训：单看总数不足以判定，必须核对分段对应关系。

**因此 Windows 穿透采用纯 Qt 路径**，按 `docs/Decisions.md` 第 8.4 节「优先使用 Qt」。收尾阶段已经删除 `WindowsWindowBackend` 的 `PassthroughStrategy` 与 `MUB_WIN_PASSTHROUGH` 环境变量，只保留继承自 `QtWindowBackend` 的实现；其中补齐 `WS_EX_TOOLWINDOW` 与 `WS_EX_NOACTIVATE` 的部分保留，与穿透路径无关。

**像素锐利的条件是乘积为整数。** 150% 缩放下 `--scale 2` 锐利，是因为 `2 x 1.50 = 3` 正好是整数物理倍率。实际生效的是 `项目倍率 x 系统 DPR`：125% 下没有任何整数倍率能得到整数物理倍率，150% 下只有偶数倍率可以。这是 `docs/Decisions.md` 第 13 节「完整的整数显示倍率集合」的直接输入，本轮不下结论。

## 阶段 5

状态：进行中

### 已完成

事件协调器 `src/core/EventCoordinator`：

- `EventKind` 的枚举值本身就是优先级，顺序由 `docs/Decisions.md` 第 4.2 节冻结：退出／隐藏 > 投喂 > 连续对话 > 单击反馈 > 自主闲聊。改顺序等于改产品行为。
- 裁决只有三种：接受、替换、抑制。**没有队列** —— 被抑制或替换的事件不会在稍后补播。
- 同类事件默认抑制，只有单击反馈允许从头重来：用户连续点击应当得到新反馈，而不是被自己上一次点击挡住；投喂则按第 3.2 节明确忽略，且没有冷却。
- `finish(kind)` 只清除正在进行的那一类，避免迟到的结束通知误清掉已经换上来的更高优先级事件。
- 对外暴露 `current()`、`lastDecision()`、`lastReplaced()`、`suppressedCount()`、`replacedCount()`，供日志与测试观察。

选择逻辑：

- `FeedingSelector` 只决定正常吃还是掉落。「投喂进行中忽略新请求」交给协调器统一裁决，不在两处各判一次。
- `ClickFeedbackSelector` 保证 `hasReaction` 恒为真；安静模式或气泡关闭时只是 `hasText` 为假，动作反馈仍在（第 3.1 节）。

接线：

- 所有行为请求都经过 `CharacterPresenter::requestEvent()`，并打日志记录请求、裁决、当前事件和被替换者。自主闲聊同样走协调器，不绕开优先级。
- 投喂期间事件独占角色：自主行为与方向映射都不参与，动画播完自动结束事件。掉落结束后立即请求连续对话，其优先级高于自主闲聊，因此闲聊会被协调器自动抑制。
- 用户暂停与事件冻结分开记账，事件结束不会覆盖用户的暂停设置。
- 角色右键菜单加了投喂的临时测试入口。同时加了退出项：无边框窗口没有关闭按钮，否则程序无法正常结束。完整菜单在阶段 7。

### 第二批：托盘、隐藏与单实例唤回

- `src/app/SingleInstance` 用 Qt 本地套接字判定唯一实例并转发唤回。判定发生在**建立任何窗口之前**，副实例不会先闪一个角色再消失。
- 端点名带用户区分后缀（由配置目录路径哈希得到）。Linux 的套接字文件默认落在共享临时目录下，只用应用 ID 会让同机另一个用户被误判成「已有实例」；后缀不把用户名原样写进套接字名。
- 遗留端点：`removeServer()` 只在连接失败之后调用，因此不会踢掉一个活着的实例。
- 启动竞态：两个进程几乎同时启动时，连不上又监听失败的一方会再连一次，连上就退为副实例。监听和连接都失败时按主实例继续运行 —— 宁可失去唤回通道，也不因为一个辅助功能拒绝启动。

### CI 补课（2026-08-27）

第三批推送后 Windows 的 `Build and test` 失败，Linux 一直是绿的。查证过程中补了三处：

- **`SingleInstance` 的唤回在 Windows 上会静默丢失**，这是产品代码的真 bug，不是测试写错。客户端原先写完就断开，Unix socket 上数据留在缓冲区里服务端照样读得到，Windows 命名管道上服务端可能读到空数据，于是消息对不上、唤回被丢弃。改为一次应答握手：服务端读满期望长度、回一个字节再断开，客户端收到应答后才关闭。
- `tst_singleinstance` 的唤回用例原先在同一个线程里直接调 `acquire()`，把主实例的事件循环一起堵住，服务端收不到连接，测的不是真实时序。改为把副实例放进单独线程 —— 产品里它本来就是另一个进程。这也是握手修好之后该用例在 Windows 上仍然失败的原因。
- `tst_desktopentry` 断言 `.desktop` 带可执行位，这条只在类 Unix 上成立：Windows 没有可执行位，Qt 只按扩展名推断。已加平台条件。
- **ctest 的 `outputOnFailure` 在 Windows runner 上抓不到 Qt Test 的输出**，失败时只有一行 `***Failed`，连通过的测试也一个字都没有，因此「没有输出」本身不构成线索。已加一个 `if: failure()` 的步骤，失败时直接跑测试可执行文件把输出打进日志。

### 单实例：判断唯一性与传递唤回分开

按计划第 12.3 节实现：

- **唯一性**：Windows 用 `Local\` 前缀的命名互斥量。它是内核对象，取得与否原子决定，进程崩溃或被强杀时由操作系统释放，不留残留。Linux 不单独加锁 —— Unix socket 端点被占用本身就是判据，遗留端点由 `QLocalServer::removeServer()` 清理，再叠一个锁文件只会多出一个要清理的残留物。
- **唤回**：两个平台一律走 Qt 本地 IPC，与锁无关。

不让套接字兼任唯一性锁的理由：那要靠「先连一次、连不上再监听」推断，中间有竞态窗口，还要自己处理残留端点。取得了锁的平台没有这个窗口，因此监听失败时不再重试连接。

锁放在 `src/platform/InstanceLock`：第 8.4 节要求平台分叉集中在窄接口里，`src/app` 不是允许出现操作系统分支的地方。接口可注入，因此两条分支在任何平台上都能测到。

`Local\` 而不是 `Global\`：桌宠是「每个桌面会话一个」，不是「每台机器一个」；用 `Global\` 会让同机另一个用户登录后起不来。

### 已知取舍：菜单打开期间对话仍在计时

第 12.1 节要求「连续对话期间打开或关闭右键菜单不结束、不翻页，也不重置当前页面」。菜单路径本身完全不触碰对话会话，因此不会翻页也不会重置。但 `QMenu::exec()` 期间事件循环继续运行，对话的打字和第 4.1 节的 20 秒无操作超时都照常计时；菜单挂满 20 秒，对话仍会按超时规则结束。

要严格满足该条，需要在菜单打开期间冻结对话，而这不能只停定时器 —— 产品用的是单调时钟，恢复时经过的时间会一次性补上，必须同时平移 `DialogueSession` 的时间基准。**项目所有者 2026-08-27 评估后决定不改**：不为「把右键菜单开着晾满 20 秒」这一种情况改动已通过测试的状态机。
