## 1. 完成定义与范围

`1.1.0` 完成必须同时满足：

- 关闭设置或关于窗口不会退出桌宠；同一种辅助窗口只能有一个实例，可以反复打开；只有明确选择“退出”才正常结束应用。
- 行为、对话、外观、窗口与桌面四组设置完整实现，普通档位、高级参数、自定义反向匹配、分组重置和全部重置符合决策。
- 设置值的校验、生效、落盘和运行中行为快照彼此分离；领域模块不接触 `QSettings`，设置窗口不直接持久化。
- 自主闲聊由独立调度器驱动，和活动状态切换、单击台词概率解耦；已有事件优先级不被破坏。
- `schemaVersion = 1`、无 schema 配置重建、未来 schema 安全回退、成对参数校验均有自动测试。
- Linux AppImage 与 Windows ZIP 的构建、测试、桌面平台插件、自检、依赖清单、许可证和对应源码自动门全部通过。
- 项目所有者只需参加本计划规定的两个人工检查点；最终检查点使用 GitHub Actions 对正式 `v1.1.0` 标签生成的原始产物。
- KDE Plasma 与 Windows 11 完成正式候选验收；GNOME 与多显示器继续明确标为未实测／接受社区 Issue 和 PR，不伪造结果。
- 启动时间、CPU、内存和长期增长在检查点 B 如实记录。按 `docs/Decisions.md` 第 14.10 节，本版**不冻结数值门槛**：三小时运行是观察手段，占用是否可接受由项目所有者在验收时判断，结论以通过／不通过记录。

不实现 `docs/Decisions.md` 第 2.4、14.7 和 14.9 节排除的功能，不借设置扩展加入角色状态、养成系统、开机自启或插件能力。

## 2. 执行原则

### 2.1 根因与变更边界

- 每个非显然改动先复现或用现有证据确认问题，追踪控制流与数据流，写出可证伪假设后再编辑。
- 修复针对根因。设置窗口关闭导致应用退出的当前假设是 Qt 默认的 `quitOnLastWindowClosed` 规则，而角色与气泡属于工具窗口；必须用生命周期测试证明，不用“关闭时改成隐藏”掩盖问题。
- 若连续尝试失败或开始出现叠加补丁，停止编辑，回到原始失败检查上游与相邻模块，形成新假设后再继续。
- `docs/Decisions.md` 是产品真相来源。实现发现决策矛盾时停止对应任务并提交证据，不在代码里自行发明规则。

### 2.2 环境与提交

- 依赖取得、配置、编译、CTest 和非图形集成测试默认在 Distrobox `dev-fedora` 内执行；不向宿主安装开发依赖。
- 宿主 KDE 与 Windows 图形测试由项目所有者执行，开发过程中不要求项目所有者反复切换系统或桌面环境。
- 每个工程阶段形成一个可独立回退的阶段性提交；不把未完成、预期失败的中间状态推到 `main`。
- 每个提交运行 `git diff --check`。新增纯逻辑必须有 Qt Test；新增设置必须同时覆盖默认值、合法值、非法值、持久化和生效边界。
- Codex 参与的提交加入 `Co-Authored-By: OpenAI Codex <noreply@openai.com>`。

### 2.3 状态记录

- 执行开始时建立 `docs/Plans/DevelopmentStatus-1.1.md`，状态只使用 `未开始`、`进行中`、`阻塞`、`已通过`。
- 工程阶段只有在本地门与对应阶段 CI 都有实际结果后才能写为 `已通过`。
- 人工检查点没有收到项目所有者结论前，不得提前填写通过。
- 状态文档记录提交、Actions run、失败根因、修复证据和实际人工环境；计划文件不反填预计结果。

## 3. 阶段性 CI 总则

阶段性 CI 是阶段退出门，不是发布前补做的附加检查。

### 3.1 每个工程阶段的固定流程

1. 在 `dev-fedora` 完成干净配置、构建、相关 Qt Test、全量 CTest 和 `--self-test`。
2. 检查 `git diff --check`，提交本阶段完整变更。
3. 推送阶段提交，等待以下两个工作流针对**同一提交**完成：
   - `.github/workflows/build.yml`：Ubuntu 22.04/GCC 与 Windows 2022/MSVC 的配置、严格警告构建、全量 CTest、未打包自检。
   - `.github/workflows/package.yml`：Release 构建与测试、Linux AppImage、Windows 便携 ZIP、实际发行目录/归档自检、依赖与许可证/对应源码审计、产物清单和 SHA-256。
4. 两个工作流的所有必需 job 都为绿色后，记录 run URL/编号和提交哈希，阶段才通过。

如果工作流因 GitHub、Qt 镜像或网络暂时故障失败，应确认失败与代码无关后重跑同一提交；代码、测试或打包门失败时必须修复并以新提交重新通过，不能把重跑当作修复。

## 4. 目标职责边界

本次不重写整个应用，沿用现有模块并补齐以下边界：

```text
SettingsWindow
    │ 只报告用户意图，不读写 QSettings
    ▼
app 层 SettingsController
    ├── 校验并维护唯一运行时 Settings
    ├── 把领域配置应用给 presenter/dialogue/animation/window
    └── 通过 SettingsStore 自动保存（按完成编辑/去抖）

SettingsStore ── 只负责 schema 1 编解码与配置后端

运行时消费者
    ├── AutonomousBehavior：新行为读取配置快照
    ├── ChatterScheduler：独立完整间隔与概率判定
    ├── ClickFeedbackSelector：下一次单击读取概率
    ├── DialogueSession：下一次对话读取会话配置
    └── AnimationPlayer/clip policy：下一次动画读取帧时长
```

约束：

- `core::Settings` 按行为、对话、外观、窗口领域分组；只保存实际参数，不另存普通层预设名。
- 档位映射和反向匹配是纯逻辑，可脱离 Widgets 测试。
- `SettingsStore` 不调用运行时对象；领域模块不引用 `QSettings`。
- 应用层统一组装依赖。不得让 `SettingsWindow` 直接调用 presenter、dialogue 或存储后端。
- 当前动作只使用开始时的配置快照。设置改变不重算截止时间、不改变进行中的移动速度、不重启动画和对话。
- 事件协调器仍是事件冲突的唯一优先级裁决点；自主闲聊调度器只产生请求，不绕过协调器直接显示气泡。
